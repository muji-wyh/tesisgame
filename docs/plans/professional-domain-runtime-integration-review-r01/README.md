## Actual lifecycle requirements and specific risks

1. **Publish only the current preparation.** On policy completion, match owner instance, selection and request; check the registered token, resolve once, then emit `theme_selected`. Recheck after that synchronous signal before `media.request_module`. In `_media_completed`, check the same identity/token plus media generation before acquisition and again before `prepared`. If work becomes stale after acquisition, release the new scope exactly once. `claim` rechecks the token and transfers only the pending scope; clear loader pending content/token afterward. A claimed round's lease survives subsequent policy cancellation.

2. **Retirement must reach Play during storage.** Loader cancellation alone revokes policy/media while `ProfessionalPlay._media_prepared` may already have called `session.open_round` (`professional_play.gd:164`). Route retirement through a coordinated Play cancellation/closure before retiring the child, so pending storage opens become obsolete and a late `round_opened` cannot publish `ready` for retired content. Preserve the request-epoch and source checks in `request`, `_media_prepared` and `_round_opened`; retain the `media -> storage -> ready` phases. Avoid a new phase that current Home/busy consumers do not handle.

3. **Preserve durable settlements.** `professional_session.gd:150` `leave_round` intentionally obsoletes only open jobs; accepted event/wallet/ack jobs continue. `professional_store.gd:45` `request`, `_receive` and `_deliver` already provide deferred, generation-bound completions. Do not reconfigure or clear this store on policy cancellation. On actual application disposal, explicitly check late host callbacks, timers and deferred native retries: Store presently has no closed lifecycle or `_exit_tree`. Any close path must revoke callbacks only at disposal and preserve recoverable committed progress/outbox. Also guard partial `ProfessionalPlay.configure` failure: `_configured == false` currently permits reconnecting already-connected children/signals on another call.

4. **Exercise the real teardown boundary.** `game_ui.gd:1553` `new_round` settles previous rewards, stops views/audio and clears cards before calling `professional.claim` at line 1659, then releases `previous_media_scope` at 1664. Keep that lease ordering. A new token rejection at final claim can occur after old presentation has already been cleared; preflight current claim eligibility immediately before destructive teardown and test reentrant invalidation during teardown. If such invalidation remains possible, preserve or restore the old presentation on failure. `game_ui._exit_tree:4552` currently clears celebration/debug state only; isolated owner or view tests do not prove the combined tree's callback/reference-release order.
