# Static persistence and retirement analysis

No project module was imported or executed, and no user save, IndexedDB store, native save or wallet state was opened or changed. These observations come from source inspection. They do not assert that no notify progress exists.

Both `web/professional-progress.js` and `scripts/professional_progress.gd` key skills directly by canonical sense ID. Curriculum revision is part of the active module-context key; it is not part of a skill key. Consequently, changing the word behind `notify.inform.v` would transfer old streaks, earned flags and exposure counts to inform. A new canonical ID is required. Do not copy or merge any old notify skill into inform, even if their use overlaps in one sentence.

Stored skill validation checks an identity and supported skill/evidence shape without requiring current catalog membership. An old notify skill can therefore remain as historical data after lexical retirement. New events are checked against the selected module's current requirements, so the retired ID cannot score in a new module that contains inform. This is a static source inference, not a new persisted or crash-recovery test. Archive content provenance separately so historical IDs remain interpretable.

Requirement keys contain course, module and requirements revision. Their fingerprints contain terms/eligible skills and expression IDs, but no expression text. Reusing `expr.foundation.module02.02` with different wording must therefore be paired with a genuinely new requirements revision for all twenty affected module02 courses; new curriculum revisions are also required to distinguish active contexts and cached content. Merely changing the global curriculum revision would leave the old requirements key and its expression completion attached. Merely changing the expression wording would not alter the fingerprint at all.

Coordinate one fresh namespace with the accepted collect gathering repair, any accepted verify/ensure replacement, and other approved shared-foundation changes. This packet reserves no revision string and writes no revision. A final plan must enumerate every catalog/course/module/media-manifest or domain-policy revision reference required by the actual current implementation. Preserve unchanged modules' historical requirements as appropriate, and preserve their stable canonical skills. Do not force a new ID for unrelated unchanged senses.

Retain old notify skills, all old requirements fingerprints, old expression completion dictionaries and earned module receipts without deletion or rewriting. Do not initialize the new requirements namespace by copying old expression completions. Old earned module completion remains historically earned, while the new inform sense has no transferred evidence. Home currently counts historical completion receipts by course/module regardless of revision; module detail reads current requirements. Any later UX adjustment must represent this distinction truthfully and preserve the user's earned completion.

Event receipts are keyed by unique event ID and carry payload fingerprints. Wallet operations use retained outbox/idempotency records. Renaming or replaying an old notify event as inform would violate the intended evidence identity and can also collide with the receipt. Do not rewrite event IDs, payloads, reward receipts or outbox records. Existing earned rewards remain earned. New inform answers require new ordinary event IDs and their own evidence.

The active catalog must not retain an unreferenced notify lexeme: `tools/validate-professional-content.cjs` raises `membership.orphan` for loaded entries with zero memberships. Historical retired content belongs outside catalog-loaded envelopes; historical stored progress is a separate persistence concern. Keep the exact old entry/source/hold as durable provenance and never erase it to satisfy the active catalog auditor.

Before any future accepted activation, root must verify the actual final source and revision binding, all twenty substitutions, current expression token/focus integrity, no old-to-new skill transfer, unchanged old completions and wallet receipts, rejection of retired events in new requirements, and survival of a populated old profile. Current static findings do not constitute those runtime checks. Existing historical tests are retained and are not replayed by this packet.
